# Route Rules

> Configure routes like a CDN or reverse proxy: headers, redirects, CORS, caching, and proxying — declared per URL pattern.

Redirects, cache headers, proxying, etc the kind of behavior you would normally configure in a CDN or reverse proxy. Route rules bring that layer into your h3 app: instead of writing a separate middleware for every concern, you describe **what should happen** for groups of routes in one declarative config object:

```ts
routeRules({
  "/old/**": { redirect: "/new/**" },
  "/assets/**": { headers: { "cache-control": "s-maxage=31536000" } },
  "/api/**": { cors: true },
});
```

The `routeRules()` middleware matches every request against your patterns, applies the matching rules before the route handler runs, and exposes the merged result on `event.context.routeRules`.

> [!TIP]
> Because rules run inside the app, they work the same on every runtime h3 supports and compose with an actual CDN in front. And since rules are plain data, frameworks and build tools can act on the same config — see [Data-Only Rules](#data-only-rules) and the [compiler](#build-time-compiler).

Route rules live in the `h3/rules` subpath. Two rules that need extra dependencies are opt-in via their own subpaths — caching (`h3/rules/cache`) and proxying (`h3/rules/proxy`) — and build-time codegen lives in `h3/rules/compiler`.

## Quick Start

```ts [server.mjs]
import { H3, serve } from "h3";
import { routeRules } from "h3/rules";
import { cache } from "h3/rules/cache"; // only needed for `cache` / `swr` rules (requires ocache)
import { proxy } from "h3/rules/proxy"; // only needed for `proxy` rules

const app = new H3();

app.use(
  routeRules(
    {
      "/blog/**": { swr: 60 },
      "/old/**": { redirect: { to: "/new/**", status: 301 } },
      "/api/proxy/**": { proxy: "https://example.com/**" },
      "/assets/**": { headers: { "cache-control": "s-maxage=31536000" } },
      "/api/**": { cors: true },
      "GET /api/cached/**": { swr: 60 }, // applies to GET only
    },
    { handlers: { cache, proxy } },
  ),
);

serve(app);
```

## Built-in Rules

| Rule       | What it does                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `headers`  | Set response headers.                                                                                                           |
| `redirect` | Send a server-side redirect.                                                                                                    |
| `cors`     | Handle CORS with [`handleCors`](/utils/security#handlecorsevent-options). Preflight (`OPTIONS`) requests are answered directly. |
| `cache`    | Cache the matched route handler's response. Opt-in, see [Caching](#caching).                                                    |
| `swr`      | Shortcut for `cache: { swr: true, maxAge?: number }`.                                                                           |
| `proxy`    | Forward the request to another origin or an in-app path. Opt-in, see [Proxying](#proxying).                                     |

> [!NOTE]
> There is deliberately no `auth` rule. Route rules are a declarative config layer; a credential check belongs in middleware where it can validate against your user store — use [`basicAuth`](/utils/security#basicauthopts) or your own middleware. If you still want an auth gate as a rule, write a [custom rule handler](#custom-rule-handlers) and read [Security](#security) first (especially `restricting`).

### `headers`

Sets headers on the **final** response — after `cache`, `redirect`, and `proxy` — so a `cache-control` set here wins over one produced by the cache handler.

```ts
routeRules({
  "/assets/**": { headers: { "cache-control": "s-maxage=31536000" } },
});
```

### `redirect`

Use a plain string for a `307` redirect, or `{ to, status }` for full control:

```ts
routeRules({
  "/old/**": { redirect: "/new/**" }, // /old/a?x=1 → /new/a?x=1 (307)
  "/search": { redirect: "https://example.com/s?lang=en" }, // /search?q=h3 → …/s?lang=en&q=h3
  "/legacy": { redirect: { to: "/", status: 301 } },
});
```

Two useful behaviors (shared with [`proxy`](#proxying)):

- **Wildcard tails:** when both the rule key and `to` end in `/**`, the matched tail is appended to the target.
- **Query forwarding:** the request's query string is forwarded verbatim (duplicate keys and encoding preserved), appended after any query already baked into the target.

### `cors`

Pass `true` for permissive defaults, or a `CorsOptions` object (origin allowlist, `credentials`, `maxAge`, …):

```ts
routeRules({
  "/api/**": { cors: { origin: ["https://example.com"], credentials: true } },
});
```

> [!NOTE]
> `cors: true` normalizes to an empty options object (`{}`). On a more specific pattern it therefore shallow-merges with options inherited from broader patterns instead of restoring permissive defaults. Use `cors: false` to reset inherited CORS entirely.

### `cache` and `swr`

Cache the matched route handler's response. These rules need a registered cache handler — see [Caching](#caching) for setup and details.

`swr: 60` is a shortcut for `cache: { swr: true, maxAge: 60 }`. `swr: 0` is valid, and `swr: false` resets an inherited `cache` rule.

### `proxy`

Forward matching requests elsewhere. This rule needs the opt-in handler from `h3/rules/proxy` — see [Proxying](#proxying).

## How Matching Works

Patterns are matched with [🌳 Rou3](https://github.com/h3js/rou3) — the same engine as [routing](/guide/basics/routing) — against `event.url.pathname`.

Unlike route handlers, where only the most specific match wins, **every matching pattern applies**. Matches are merged from least to most specific: object options shallow-merge (more specific keys win), any other value overrides wholesale.

```ts
routeRules({
  "/**": { headers: { "x-app": "demo" } },
  "/api/**": { headers: { "x-api": "1" } },
});

// GET /api/users → x-app: demo, x-api: 1
```

### Resetting a Rule

Set a rule to `false` on a more specific pattern to remove it there:

```ts
routeRules({
  "/api/**": { cors: { origin: ["https://example.com"] } },
  "/api/public/**": { cors: false }, // no CORS handling under /api/public
});
```

### Method-Scoped Rules

Prefix a key with an HTTP method to scope it. A key without a method applies to all methods; method-scoped rules merge after (and can override) the method-agnostic ones. The method token is case-insensitive.

```ts
routeRules({
  "/api/**": { headers: { "x-api": "1" } }, // any method
  "GET /api/**": { swr: 60 }, // GET only
});
```

Rules are grouped by the _route_ a pattern resolves to, not by its text — `/users/*`, `/users/:id`, and `/users/:userId` are one group, so a method-agnostic rule written with one spelling still applies alongside a method-scoped rule written with another.

> [!NOTE]
> When two spellings of one route differ in specificity (`/a/*` vs `/a/:id`), the more general pattern is resolved last and wins, whether or not either is method-scoped. Prefer a single spelling per route.

### Reading Matched Rules

The merged result is available in handlers and middleware as `event.context.routeRules`, keyed by rule name. Each entry is the merged rule options — what you authored, with more specific patterns merged in and shortcuts like `swr` expanded:

```ts
app.get("/blog/:slug", (event) => {
  const rules = event.context.routeRules;
  rules?.cache; // { swr: true, maxAge: 60 }
  rules?.redirect?.to; // "/new"
  rules?.headers?.["x-a"]; // "1"
});
```

> [!IMPORTANT]
> Match results are [memoized](#memoization) by default, so the object on the context is shared across requests. Treat it (and the rule options it holds) as **read-only**.

The context does not say _which_ pattern a rule came from. If you need that provenance (the contributing pattern and its params), use a [matcher](#using-matchers-directly) directly:

```ts
const { routeRules, matchedRules } = matcher("GET", "/blog/post");
routeRules.cache; // { swr: true, maxAge: 60 } — same object the context gets
matchedRules.cache?.route; // "/blog/**"
matchedRules.cache?.params; // rou3 params of the contributing patterns
```

You can register multiple `routeRules()` instances and they compose: each merges its matched rules **over** whatever an earlier instance already put on the context (later instances win per rule name). A framework-level rule set and an app-level one can coexist.

### Data-Only Rules

Any key without a handler (`prerender`, `isr`, or your own) is **data-only**: it flows through matching and merging like any other rule and is readable from `event.context.routeRules`, but has no runtime behavior. This is handy for build-time tools and frameworks that act on the config themselves.

```ts
routeRules({
  "/docs/**": { prerender: true },
});

// event.context.routeRules.prerender → true
```

To type data-only keys, declare them once — see [TypeScript](#typescript).

## Caching

H3 ships **no caching implementation** in `h3/rules`: the `cache` rule (and the `swr` shortcut) require a registered `cache` handler, and matcher construction throws if a rule set uses them without one.

The ready-made handler is backed by [ocache](https://github.com/unjs/ocache) and lives in `h3/rules/cache`. ocache is an **optional peer dependency** — install it alongside `h3`. Keeping the handler in its own subpath means ocache stays out of every bundle that does not cache.

```ts
import { routeRules } from "h3/rules";
import { cache } from "h3/rules/cache";

// default: in-memory storage
app.use(routeRules({ "/blog/**": { swr: 60 } }, { handlers: { cache } }));
```

To customize storage or defaults, create a handler instance:

```ts
import { createOcacheRuleHandler } from "h3/rules/cache";

app.use(
  routeRules(rules, {
    handlers: {
      cache: createOcacheRuleHandler({
        storage: myStorage, // ocache storage instance (or a factory), shared by every rule
        defaults: { staleMaxAge: 60 }, // ocache defaults incl. hooks (rule options win)
      }),
    },
  }),
);
```

### How Entries Are Keyed

The `cache` rule wraps the **matched route handler**, so it only applies where a route matched. Entries are stored under the `"h3/route-rules"` group with a `<handlerScope>:<method>:<rulePattern>:<matchedRoute>` name by default:

- The **scope** is unique per handler instance and per matched route handler, so two apps or two matchers never read or write each other's entries — even when they share the module-scoped `cache` export.
- The **method** keeps a body-less `HEAD` response out of the `GET` entry.

Both `group` and `name` are plain `cache` rule options and can be overridden — but an explicit `name` replaces the whole default, isolation included.

The scope is not stable across processes, so a **persistent** storage backend gets repopulated per process and is not shared between workers. Pass `createOcacheRuleHandler({ id: "my-app" })` for stable keys — but only when that instance serves a single app.

> [!NOTE]
> ocache gives every cached handler a storage instance of its own. `createOcacheRuleHandler` instead points all of its rules at one store — the `storage` you pass, or a memory store created on the first cached request — so an app's routes share a single bounded cache. Two instances built with the same `id` share that default store as well, since their keys already match.

### What Reaches a Cached Handler

A cached handler only ever sees request data the cache key covers, so an entry can never depend on something it was not keyed by:

- **Query strings are dropped** by default — the handler receives a query-less URL and the query does not vary the key. Set `allowQuery: ["page", "q"]` to allowlist names, or `allowQuery: true` for the whole query string.
- **Headers** are dropped unless named in `varies` (see [Credentials and Cookies](#credentials-and-cookies) for the credential rules). That includes conditional, tracing, and request-id headers — read those in middleware outside the cache rule.
- A response is **served but not stored** when it declares a `Vary` name the key does not cover, sets `Cache-Control: no-store`/`private`/`no-cache`, has a non-`200`/`203`/`301`/`308` status, or exceeds `maxBodySize`.

Resolving a cached entry has a **30 second deadline** (`maxResolveTime`); on expiry every waiter is rejected and the entry evicted. The handler's `event.req.signal` aborts with it, so a handler doing its own upstream `fetch` should forward the signal.

### Credentials and Cookies

> [!IMPORTANT]
> `Cookie`, `Authorization`, and `Proxy-Authorization` are **stripped** from the request the cached handler sees. None of them varies the auto-generated cache key — without stripping, a handler rendering per-user content from a bearer token would have it cached anonymously, served to everyone, and advertised `public, s-maxage=N` to shared caches.

- Set `cache: { allowAuthorization: true }` to let the credential through. It then participates in caching (hashed into the key, merged into `Vary`), so each credential gets its own entry.
- If the runtime makes it impossible to remove the credential headers (immutable request headers _and_ a request that cannot be rebuilt), the cache rule fails the request with a `500` rather than caching a credentialed response under a credential-free key.
- Headers listed in `varies` remain visible to the cached handler. Since they are part of the key and the response's `Vary`, each value gets its own entry. A credential named in `varies` is the exception and stays stripped — `allowAuthorization` is the only switch that forwards one.
- A handler's `Set-Cookie` reaches only the requester whose request produced it and **never enters the cache entry** — otherwise one visitor's session would replay to everyone. `allowCookies` is request-side only: it names which cookie crumbs key the entry and reach the handler. A route that must set a cookie on every response should not be cached.

### Cache-Control Behavior

- A handler-set `Cache-Control` declaring `private` or `no-store` is preserved as-is (ocache also refuses to store such a response).
- Any _other_ handler-set `Cache-Control` is replaced by the rule's synthesized `public, max-age=N, s-maxage=N`. Use a `headers` rule to control the final header.
- Pass `sendCacheControl: false` to suppress the synthesized header.

### Bring Your Own Cache

To plug in a different caching implementation (no ocache at all), build a handler from the core factory. `defineCachedHandler` receives the matched route handler plus the merged rule options (with `group` / `name` pre-filled) and returns the cached wrapper — this is the integration point for frameworks such as Nitro:

```ts
import { createCacheRuleHandler } from "h3/rules";

const cache = createCacheRuleHandler({
  defineCachedHandler: (handler, opts) => myCachedHandler(handler, opts),
});
```

The declarative rule options (`RouteRuleConfig["cache"]`) are the ocache-compatible `CacheRuleOptions` schema owned by h3. Implementation hooks (`getKey`, `shouldCache`, `getMaxAge`, …) are not rule data — pass them via the handler factory's `defaults`.

## Proxying

Like caching, the `proxy` rule is **opt-in**: its handler imports [`proxyRequest`](/utils/proxy#proxyrequestevent-target-opts), so it lives in `h3/rules/proxy` and stays out of bundles that do not proxy. Register it explicitly — matcher construction throws if a rule set uses `proxy` without a handler:

```ts
import { routeRules } from "h3/rules";
import { proxy } from "h3/rules/proxy";

app.use(
  routeRules({ "/api/proxy/**": { proxy: "https://example.com/**" } }, { handlers: { proxy } }),
);
```

Targets follow the same rules as [`redirect`](#redirect): `/**` tails are appended and the query string is forwarded.

> [!TIP]
> To keep `cache` or `proxy` deliberately data-only (matched and readable from the context, but with no runtime behavior), pass `handlers: { cache: undefined }` / `handlers: { proxy: undefined }` instead of a handler.

## Execution Order

Rules with runtime behavior run as middleware, outermost first:

```
cors (-3) → [-2 free] → headers (-1) → custom rules (0) → redirect (1) → proxy (2) → cache (3) → route handler
```

What this means in practice:

- A CORS preflight is answered before anything else runs.
- `headers` wraps the response of every inner rule (that is how it wins over a cache-produced `cache-control`).
- `redirect`, `proxy`, and `cache` answer without calling the next rule, so each owns a distinct order — the innermost of them (`cache`) is the one that dispatches the route handler.
- Because `cache` dispatches the route handler itself, it also ends the app's _global_ middleware chain — see [Cached Routes and Global Middleware](#cached-routes-and-global-middleware).
- A custom rule left at the default order `0` runs before all three terminators, whichever patterns each was authored on.

`order` is a plain number (lower runs first), so a custom handler can sit anywhere. `-2` is deliberately left free for a rule that should short-circuit ahead of `headers`, `redirect`, `proxy`, and `cache`. Rules that share an order run in rule-name order — deterministic, but arbitrary: give a handler that can short-circuit an explicit order rather than relying on it. See [Security](#security) for what ordering implies.

## Options

`routeRules(config, options)` accepts:

| Option     | Description                                                                                         |
| ---------- | --------------------------------------------------------------------------------------------------- |
| `baseURL`  | Prefix every rule pattern (trailing slash trimmed).                                                 |
| `handlers` | Add or override rule handlers by name. `undefined` makes that rule data-only.                       |
| `memoize`  | Memoize match results per `method + pathname`. Enabled by default, see [Memoization](#memoization). |
| `preMerge` | Resolve each pattern's subsumption chain at startup, see [Pre-merging](#pre-merging).               |

## Custom Rule Handlers

A rule handler is `{ handler, order? }`:

- `handler` builds an H3 [middleware](/guide/basics/middleware) from the matched rule.
- `order` controls execution order (lower runs first, default `0`; the built-ins occupy `-3`…`-1` and `1`…`3`, see [Execution Order](#execution-order)).

The matched rule the handler receives is a wrapper — `{ options, route, params?, handler? }` — so it sees the merged `options` plus the provenance the context does not carry (`route` is the most specific pattern that contributed).

```ts
app.use(
  routeRules(
    { "/x/**": { shout: "hello" } },
    {
      handlers: {
        shout: {
          handler: (matched) => (event) => {
            event.res.headers.set("x-shout", String(matched.options).toUpperCase());
          },
        },
      },
    },
  ),
);
```

> [!IMPORTANT]
> A custom handler that **restricts** access (an auth gate, a rate limit, an IP allowlist) must also set `restricting: true` — see [Security](#security) for why.

## Performance

### Memoization

For a given `method + pathname` the merged result is fully deterministic, so `routeRules()` memoizes it **by default**: repeat requests skip rule lookups, path canonicalization, merging, and middleware construction — a hot path becomes a single map lookup.

- Entries are capped at `1024` by default with FIFO eviction, so unbounded dynamic paths cannot grow the cache. Tune with `memoize: { max }`.
- Pass `memoize: false` to resolve every request from scratch (each request then gets fresh result objects).

For the lower-level matchers, memoization is decoupled from construction — opt in by wrapping any matcher with `memoizeRouteRulesMatcher(matcher, opts?)`, so an un-memoized bundle can tree-shake it away.

### Pre-merging

`preMerge: true` resolves each pattern's subsumption chain up front (at matcher startup, or at build time via the [compiler](#build-time-compiler)) so per-request resolution takes only the most specific matched layer instead of merging all matched layers. Method-scoped and method-agnostic rules, `false` resets, and per-rule `params` behave exactly as with the default per-request merge.

Pre-merging requires an unambiguous rule set. If two patterns partially overlap (for example `/a/*/c` and `/a/b/*`, where the most specific match would be ambiguous) or use patterns it cannot analyze (regex params):

- The **runtime matcher throws at startup**.
- The **compiler is fail-safe**: it logs a warning and falls back to plain compilation, so the build still produces a correct matcher.

## Using Matchers Directly

`routeRules()` is the plug-and-play entry point. The pieces underneath are exported too, for framework integrations that need to match rules outside the middleware:

```ts
import { createRouteRulesMatcher, normalizeRouteRules, memoizeRouteRulesMatcher } from "h3/rules";
import { cache } from "h3/rules/cache";

const matcher = memoizeRouteRulesMatcher(
  createRouteRulesMatcher(normalizeRouteRules(config), {
    baseURL: "/base",
    preMerge: true,
    handlers: { cache },
  }),
);

const { routeRules, routeRuleMiddleware } = matcher("GET", "/blog/post");
```

- `normalizeRouteRules()` expands shortcuts (`swr`), normalizes string and boolean forms, and canonicalizes keys. Unlike `routeRules()`, `createRouteRulesMatcher()` takes **normalized** rules — that keeps normalization out of runtime bundles that don't need it.
- A match result is `{ routeRules, matchedRules, routeRuleMiddleware }`: the merged options map (what `routeRules()` puts on the context), the same rules with their provenance, and the ordered middleware chain.
- `mergeMatchedRouteRules()` is the pure merge step (matched layers in, matched rules out), and `ruleHandlers` is the default handler registry (`headers`, `redirect`, `cors`).

## TypeScript

There are two interfaces, one per end of a rule: `RouteRuleConfig` describes what you **author**, `RouteRules` what the merge **resolves**. Since the merged value is the config value, a custom rule is declared once, in one shape, on both:

```ts
declare module "h3/rules" {
  interface RouteRuleConfig {
    /** Incremental Static Regeneration (handled at build time). */
    isr?: number | boolean;
    /** Add this route to the prerender queue. */
    prerender?: boolean;
    /** A data-only rule with no runtime handler. */
    audience?: "public" | "internal";
  }
  interface RouteRules {
    isr?: number | boolean;
    prerender?: boolean;
    audience?: "public" | "internal";
  }
}

// event.context.routeRules.audience → "public" | "internal" | undefined
```

Key points:

- `RouteRuleConfig` is **closed** — unknown keys are compile errors, so a typo like `redirct` is caught at build time. The augmentation is what re-opens it for your key.
- `RouteRules` types the merged rules everywhere they surface: `event.context.routeRules`, a matcher's `routeRules`, and (as each rule's `options`) the `matchedRules` a rule handler receives.
- Data-only rules flow through normalization and merge untouched at runtime — augmentation only affects the typing.
- `RouteRules` is h3's own interface, re-exported by `h3/rules`, so `declare module "h3"` merges into the same declaration — the spelling Nitro and the standalone `h3-rules` package already use. Only `RouteRuleConfig` is exclusive to `h3/rules`.

### Redeclaring Built-in Rules

You can also redeclare one of h3's **built-in** keys, not just add new ones. A framework carrying its own rule shape can re-type `redirect`, `proxy`, … and that key then resolves to the augmenter's type instead of h3's:

```ts
declare module "h3" {
  interface RouteRules {
    redirect?: string | { to: string; status?: number };
    cors?: boolean;
  }
}
```

Any shape is accepted, including primitive and `false` arms. `RouteRules` is unconstrained; h3's built-ins live on a separate `BuiltinRouteRules` and are composed in only for the keys nobody redeclared. The type on the context is that composition, exported as `ResolvedRouteRules`. A redeclaration **replaces** h3's built-in rather than intersecting with it, and a key left to h3 keeps its exact option type, so `rules.redirect?.to` reads without narrowing.

> [!NOTE]
> h3 composes in only its own built-ins and declares no index signature. Contributing a blanket `[key: string]: unknown` to the shared interface would turn every other module's augmentation into a type error — which is why an undeclared data-only key is readable at runtime but not typed until you declare it.

Two more types are exported for integrations: `NormalizedRouteRules` (one pattern's rules after `normalizeRouteRules()` — `RouteRules` plus `false` resets and arbitrary names) and `MatchedRouteRule` (a merged rule with its provenance, what a rule handler receives).

## Security

Route rules often gate or shape sensitive behavior, so the matcher takes several precautions by default. You mostly don't need to do anything — but read this section if you write a custom rule handler that restricts access.

### Encoded and Alternate Path Spellings

A rule is matched against **every spelling of the request path a consumer can resolve**, not just the one h3 dispatched on — otherwise a rule could be dodged by re-spelling the path it applies to.

[`event.url.pathname`](/guide/api/h3event#pathname-encoding) decodes only the escapes whose character survives URL serialization (so `/%40admin` is already served as `/@admin`), but still carries others encoded: the separators (`%2f`, `%5c`), `%25` at any nesting depth, escapes the serializer would re-add (`%20`, non-ASCII), and C0 controls. Patterns, meanwhile, are written with the character itself. So each request is also resolved against:

- its **canonical** reading (encoded separators decoded, `.` / `..` resolved),
- its **slash-merged** reading (what a downstream like nginx `merge_slashes` resolves),
- its **percent-decoded** reading.

```ts
routeRules({
  "/@admin/**": { redirect: "/elsewhere" },
  "/a admin/**": { redirect: "/elsewhere" },
});

// GET /@admin/data     → matched
// GET /%40admin/data   → matched  (h3 serves it as /@admin/data)
// GET /a%20admin/data  → matched  (a proxied backend would serve it as "/a admin/data")
// GET /a%2520admin/x   → matched  (…and so would one that decodes twice)
// GET /admin%2fpanel   → matched against /admin/panel too
```

An alternate reading may only **add** a rule, or override one with an equal-or-more-specific pattern — a broader pattern reached through a crafted path can never downgrade a rule the served path resolved.

The reverse spelling is normalized too: a pattern written `/a%20admin/**` is decoded to `/a admin/**` at config time, so it does not silently cover only the encoded form. A rule key resolves escapes exactly as an h3 route pattern does, so an escaped rou3 metacharacter _becomes_ that metacharacter — `"/a/%3Aid"` is the `:id` param pattern, and `"/f/%2A%2A"` a catch-all, matching `app.get("/a/%3Aid")`. Only `%2f`, `%5c`, and `%25` stay encoded and match literally, since decoding one would change the pattern's segment count.

Dispatch is unaffected: routing still uses `event.url.pathname` as served, and `redirect` / `proxy` still forward the raw path bytes.

### Resets and the `restricting` Flag

A rule the served path _reset_ with `false` needs special care across alternate readings. A reset is applied as a deletion, so a reset rule would otherwise be indistinguishable from one that never matched, and a broader alternate reading would re-add it. The matcher decides by the rule's **polarity**:

- A rule that **permits** something stays reset. Re-adding it could only loosen the response, so the exemption wins — a `cors: false` on a private subtree cannot be undone by a crafted spelling of the same path. Every built-in (`cors`, `redirect`, `headers`, `cache`, `proxy`) is of this kind.
- A rule that **restricts** something is still re-added. A restriction is fail-closed, so an exemption granted by a single-segment pattern does not follow a path that decodes to more segments than that pattern covers.

Handlers declare which they are via `RuleHandler.restricting`, which defaults to `false`. No built-in sets it.

> [!IMPORTANT]
> A **custom** rule handler that restricts (an auth gate, a rate limit, an IP allowlist) must set `restricting: true`, or a `false` reset on one reading will exempt it on every other reading. The default is the safe choice for a permission and the wrong one for a restriction, and nothing warns. Rules with no handler at all (data-only rules a consumer such as Nitro acts on itself) cannot carry the flag — a consumer treating one as a gate needs its own reasoning at the point of use.

One residual, in the fail-safe direction: a permission reset is never resurrected, even by a reading that is a faithful re-spelling of the path that granted it. `{"/**": { cors }, "/app/*": { cors: false }}` keeps the exemption on `/app/a%2fb`, whose decoded reading has two segments and arguably falls outside the single-segment pattern that reset it. Every case this gets wrong errs toward _not_ applying a permission.

### `HEAD` and Preflight Requests

`HEAD` requests are served by the matching `GET` route ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#name-head)), so `GET`-scoped rules apply to `HEAD` too — otherwise a rule keyed `GET /admin/**` could be dodged with a `HEAD` request. An explicit `HEAD` key still merges over (and can reset) the `GET` ones.

A CORS preflight arrives as `OPTIONS`, so a `cors` rule scoped to the method the browser announces in `Access-Control-Request-Method` is resolved for the preflight as well. Only the `cors` rule is taken from that lookup — never any other rule scoped to that method, since browsers send preflights without credentials and a gate lifted out of it would reject every preflight.

### Headers on Short-Circuited Responses

`headers` sits at order `-1`, so it wraps every rule that runs inside it — but not one that runs _outside_ it. A response produced by an outer rule (the `cors` preflight answer, or a custom handler in the free `-2` band) short-circuits before the headers middleware is entered, so the `headers` rule is not applied to it. Every other response goes through it, including error responses raised further in (a `404`, or a handler that throws).

If a header must be present on such a response too, set it from global middleware registered before `routeRules()`, and set it on `event.res.errHeaders` as well — an error response is built from that bag, not from `event.res.headers`.

### Cached Routes and Global Middleware

The `cache` rule dispatches the matched route handler itself instead of calling the next layer, so **global middleware registered after `routeRules()` never runs for a route a `cache` rule matched** — on a cache _miss_ just as much as on a hit:

```ts
app.use(routeRules({ "/api/**": { swr: 60 } }, { handlers: { cache } }));
app.use(requireAuth); // never runs for /api/** — not even on the first request
app.get("/api/private/:id", handler);
```

Register `routeRules()` **after** every global middleware that has to run for cached routes:

```ts
app.use(requireAuth); // runs first, for every request
app.use(routeRules({ "/api/**": { swr: 60 } }, { handlers: { cache } }));
```

Per-route middleware is unaffected — it is part of the composed route handler the cache rule dispatches, so it runs on a miss and is cached along with the response (which is its own reason not to put a credential check there). `redirect` and `proxy` end the chain too, but they answer the request outright and never reach the route handler, so this is only surprising for `cache`.

That same composition is why `routeRules()` belongs in `app.use()`, not on a route:

```ts
// Works, but the whole rule chain runs twice per request:
app.get("/api/x", handler, { middleware: [routeRules(rules, { handlers: { cache } })] });
```

Registered this way (or composed in with `defineHandler({ middleware })`), the rule sits inside the very handler the `cache` rule dispatches, so the dispatch re-enters it. The rule detects the re-entry and continues to the route handler instead of dispatching a second time — the response and the caching are correct — but every other matched rule still runs on both passes. Keep `routeRules()` global.

### Redirect and Proxy Target Safety

For a `/**` target, the matched tail is appended and the resulting path is checked against the target's own base; a request that would escape it (for example via an encoded `..%2f` traversal) is rejected with `400`.

The tail is taken by stripping the rule key's prefix, counted in segments, so that count has to be the same for every request the key matches. A prefix segment that matches a variable number of segments — a catch-all (`/a/**/old/**`), a modifier param (`/:lang?/old/**`, `/x/:seg*/old/**`), or a group spanning a separator (`/x{/a}?/old/**`) — has no fixed count, and such a request is rejected with `400` rather than forwarded with a mis-stripped path. Plain params, `*`, regex params, and intra-segment groups (`/:lang/old/**`, `/x/*/old/**`, `/blog{-:title}?/old/**`) each match exactly one segment and work as expected.

### CORS Credentials

`credentials: true` requires an explicit `origin` (allowlist or validation function). Combining it with a wildcard origin throws at startup, since `Access-Control-Allow-Origin: *` is invalid for credentialed requests.

## Build-Time Compiler

For build-time codegen, compile a rule set into a `findRouteRules` function so Rou3 stays out of the runtime bundle:

```ts
import { compileRouteRules } from "h3/rules/compiler";

const mod = compileRouteRules(config, {
  preMerge: true, // optional: bake pre-merged chains into the generated matcher
});

mod.code; // whole module (also `String(mod)` / template interpolation)
// -> import { headers as __ruleHandlers__$headers } from "h3/rules";
// -> export const findRouteRules = (method, path) => ...;
```

`compileRouteRules` returns the module split into its two composable halves — `imports` (the handler `import` statements) and `body` (the `export const findRouteRules = …` declaration) — plus `code` (the whole module, same as `String(mod)`). Take `code` to write a standalone module, or hoist `imports` and inline `body` to weave the matcher into a larger generated module.

The compiler entry points normalize their input themselves (compilation is build-time, so the pass is free) — pass authored config directly. An already-normalized rule set is equally valid input, since normalization is idempotent.

At runtime, wrap `findRouteRules` with `createMatcherFromFind(findRouteRules)`, composing `memoizeRouteRulesMatcher` around it for [memoization](#memoization). Compiled and runtime matchers produce identical results.

> [!IMPORTANT]
> The matcher API takes the method **already uppercased** — `findRouteRules`, `createMatcherFromFind`, and `createRouteRulesMatcher` all compare it as given. The `routeRules()` middleware normalizes for you; a hand-written wrapper must pass `event.req.method.toUpperCase()`, or a lowercase-spelled request will match no method-scoped rule at all and skip its gate.

> [!NOTE]
> Rule options are embedded as JS object literals, so they must survive a JSON round-trip. A function, `Date`, or `RegExp` in a rule option (for example a `cors.origin` validation function) fails compilation with an explicit error instead of silently diverging from the runtime matcher.

### Specificity Guard

`createMatcherFromFind` applies a **specificity guard by default**. When one of a path's [alternate readings](#encoded-and-alternate-path-spellings) (canonical, slash-merged, percent-decoded) resolves a rule differently from the served path, the alternate reading may only override with an equal-or-more-specific pattern — so a broad `/**` rule can never downgrade a narrower `/admin/**` one on a crafted `%2f` / `%2e%2e` path.

The default guard is dependency-free, so a compiled bundle stays free of Rou3. It decides containment from pattern shape, which is a **conservative approximation** of the exact relation: it allows only containment it can prove, so it never permits an override the exact relation would reject — but it is stricter. Where it cannot decide (a named catch-all such as `**:rest`, a regex or partial param, or a modifier param like `:page?` / `:path*`), it keeps the rule the served path resolved rather than applying the narrower one.

Use [`matcher: true`](#matcher-export) to have the compiler bake the exact relation into the generated module — recommended whenever rule keys use modifier params — or pass your own predicate as the second argument, or `() => true` to disable the guard.

Ordering matched layers by specificity does **not** go through this predicate: it uses a rank computed when the rule set is built, so a compiled matcher without the baked relation still resolves the same rules as the runtime matcher.

### Matcher Export

To skip the hand-written wrapper, pass `matcher` so the generated module exports a ready-to-use matcher alongside `findRouteRules`:

```ts
compileRouteRules(config, { matcher: true });
// -> export const findRouteRules = …;
// -> import { createMatcherFromFind } from "h3/rules";
// -> export const matcher = createMatcherFromFind(findRouteRules, /* baked specificity guard */);

// rename the export, or bake in memoization:
compileRouteRules(config, { matcher: { name: "routeMatcher", memoize: true } });
// -> import { createMatcherFromFind, memoizeRouteRulesMatcher } from "h3/rules";
// -> export const routeMatcher = memoizeRouteRulesMatcher(createMatcherFromFind(findRouteRules, …));
```

`matcher: true` names the export `matcher`; pass a string to rename it, or `{ name?, memoize? }` to also wrap it in `memoizeRouteRulesMatcher` (`memoize: { max }` tunes the cap). `memoizeRouteRulesMatcher` is imported **only** when `memoize` is set, so an un-memoized matcher export still tree-shakes it away. The infra import counts toward `mod.imports`.

### Handler Sources

The generated module imports **only the rule handlers the rule set uses**. Most built-ins are a named export of `h3/rules` (`headers`, `redirect`, `cors`), except the opt-in subpath handlers: `cache` comes from `h3/rules/cache` and `proxy` from `h3/rules/proxy`, so their dependencies only enter the bundle when a matching rule exists.

Where each handler is imported from is controlled by `runtimeRules` — a record keyed by rule name whose value is either a module id (the module must export a member named exactly as the rule key) or `{ source, export }` when the export is named something else. It is merged **over** the built-in preset (`DEFAULT_RUNTIME_RULES`), so you only list what you add or change. Handlers sharing a source collapse into one import statement:

```ts
import { compileRouteRules } from "h3/rules/compiler";

compileRouteRules(config, {
  runtimeRules: {
    cache: "#nitro/cache", // repoint the built-in cache at your own module
    isr: { source: "#nitro/rules", export: "handleISR" }, // custom rule + export
  },
});
// -> import { handleISR as __ruleHandlers__$isr } from "#nitro/rules";
// -> import { cache as __ruleHandlers__$cache } from "#nitro/cache";
// (redirect, headers, … still import from "h3/rules" when used)
```
