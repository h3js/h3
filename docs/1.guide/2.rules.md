# Route Rules

> Declaratively attach behavior to route patterns: redirect, proxy, headers, cache and CORS.

Route rules describe **what should happen** for a set of URL patterns in one config object, instead of registering a handler or middleware per concern.

The `routeRules()` middleware matches every request against your patterns, runs the rules that have runtime behavior before the route handler, and exposes the merged result as `event.context.routeRules`.

Rules live in the `h3/rules` subpath. The two rules that pull extra dependencies are split out into `h3/rules/cache` and `h3/rules/proxy`, and build-time codegen into `h3/rules/compiler`.

## Quick Start

```ts [server.mjs]
import { H3, serve } from "h3";
import { routeRules } from "h3/rules";
import { cache } from "h3/rules/cache"; // only for `cache` / `swr` rules (requires ocache)
import { proxy } from "h3/rules/proxy"; // only for `proxy` rules

const app = new H3();

app.use(
  routeRules(
    {
      "/blog/**": { swr: 60 },
      "/old/**": { redirect: { to: "/new/**", status: 301 } },
      "/api/proxy/**": { proxy: "https://example.com/**" },
      "/assets/**": { headers: { "cache-control": "s-maxage=31536000" } },
      "/api/**": { cors: true },
      "GET /api/cached/**": { swr: 60 }, // method-scoped
    },
    { handlers: { cache, proxy } },
  ),
);

serve(app);
```

## Available Rules

| Rule       | Behavior                                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `headers`  | Set response headers.                                                                                                          |
| `redirect` | Server-side redirect.                                                                                                          |
| `proxy`    | Proxy the request to another origin or an in-app path. Opt-in handler, see [Proxying](#proxying-h3rulesproxy).                 |
| `cache`    | Wrap the matched route handler with a cached handler. Opt-in handler, see [Caching](#caching-h3rulescache).                    |
| `swr`      | Shortcut for `cache: { swr: true, maxAge?: number }`.                                                                          |
| `cors`     | Handle CORS via [`handleCors`](/utils/security#handlecorsevent-options). Preflight (`OPTIONS`) requests are answered directly. |

> [!NOTE]
> There is no authentication rule. Route rules are a declarative, serializable
> config layer — a credential check belongs in middleware, where it can validate
> against your own user store: use [`basicAuth`](/utils/security#basicauthopts)
> (or your own middleware) on the routes that need it. If you do want an auth
> gate expressed as a rule, register a [custom handler](#custom-rules)
> and read [Security](#security) first — in particular `restricting`.

### `headers`

Applied to the **final** response, after `cache` / `redirect` / `proxy` — so a `cache-control` set here wins over one computed by the cache handler.

```ts
routeRules({
  "/assets/**": { headers: { "cache-control": "s-maxage=31536000" } },
});
```

### `redirect`

A plain string is the target with status `307`, or use `{ to, status }`. When both the rule key and `to` end in `/**`, the matched tail is appended.

```ts
routeRules({
  "/old/**": { redirect: "/new/**" }, // /old/a?x=1 -> /new/a?x=1 (307)
  "/search": { redirect: "https://example.com/s?lang=en" }, // /search?q=h3 -> …/s?lang=en&q=h3
  "/legacy": { redirect: { to: "/", status: 301 } },
});
```

The request query string is forwarded verbatim (duplicate keys and encoding preserved), appended after any query baked into the target. The same target rules apply to [`proxy`](#proxying-h3rulesproxy).

### `cors`

`true` applies permissive defaults, or pass `CorsOptions` (origin allowlist, `credentials`, `maxAge`, …).

```ts
routeRules({
  "/api/**": { cors: { origin: ["https://example.com"], credentials: true } },
});
```

> [!NOTE]
> `cors: true` normalizes to an empty options object (`{}`), so on a more specific pattern it shallow-merges with options inherited from broader patterns rather than restoring permissive defaults. Use `cors: false` to reset inherited CORS.

### `swr`

Shortcut for `cache: { swr: true, maxAge?: number }`. `swr: 0` is valid; `swr: false` resets an inherited `cache`. Needs the [cache handler](#caching-h3rulescache).

### Execution Order

Rules with runtime behavior run as middleware, outermost first:

```
cors (-3) → [-2 free] → headers (-1) → everything else (0) → route handler
```

A preflight is therefore answered before anything else runs, and `headers` wraps the response of every inner rule. `order` is a number (lower runs first), so a custom handler can sit anywhere; `-2` is deliberately left free for a rule that should short-circuit ahead of `headers`, `redirect`, `proxy` and `cache`. See [Security](#security) for what this implies.

## How Matching Works

Patterns are matched with [🌳 Rou3](https://github.com/h3js/rou3) — the same engine as [routing](/guide/basics/routing) — against `event.url.pathname`.

Unlike route handlers, where only the most specific match wins, **every** matching pattern applies. Matched patterns are merged from least to most specific: object options shallow-merge (more specific keys win), any other value overrides wholesale.

```ts
routeRules({
  "/**": { headers: { "x-app": "demo" } },
  "/api/**": { headers: { "x-api": "1" } },
});

// GET /api/users -> x-app: demo, x-api: 1
```

Setting a rule to `false` on a more specific pattern resets it:

```ts
routeRules({
  "/api/**": { cors: { origin: ["https://example.com"] } },
  "/api/public/**": { cors: false },
});
```

### Method Scoped Keys

Keys may carry an optional HTTP method prefix. A key without a method applies to all methods; method-scoped rules merge after (override) the method-agnostic ones. The method token is matched case-insensitively.

Rules are grouped by the _route_ a pattern resolves to, not by its text, so `/users/*`, `/users/:id` and `/users/:userId` are one group — a method-agnostic rule written with one spelling still applies alongside a method-scoped rule written with another.

```ts
routeRules({
  "/api/**": { headers: { "x-api": "1" } }, // any method
  "GET /api/**": { swr: 60 }, // GET only
});
```

> [!NOTE]
> When two spellings of one route differ in specificity (`/a/*` vs `/a/:id`), the more general pattern is resolved last and wins, whether or not either is method-scoped. Prefer a single spelling per route.

### Reading Matched Rules

The merged result is exposed as `event.context.routeRules`, keyed by rule name, each entry holding the **merged rule options** — the config the rule was authored from, with more specific patterns merged in and shortcuts expanded.

```ts
app.get("/blog/:slug", (event) => {
  const rules = event.context.routeRules;
  rules?.cache; // { swr: true, maxAge: 60 }
  rules?.redirect?.to; // "/new"
  rules?.headers?.["x-a"]; // "1"
});
```

Which pattern a merged rule came from (and its params) is _not_ on the context — it is per-rule provenance, carried by the matched rules a rule handler is built from. A matcher exposes both:

```ts
const { routeRules, matchedRules } = matcher("GET", "/blog/post");
routeRules.cache; // { swr: true, maxAge: 60 } — same object the context gets
matchedRules.cache?.route; // "/blog/**"
matchedRules.cache?.params; // rou3 params of the contributing patterns
```

> [!IMPORTANT]
> Match results are [memoized](#memoization) by default, so the object on the context is shared across requests. Treat it (and the rule `options` it holds) as read-only.

Multiple `routeRules()` instances compose: each one merges its matched rules **over** whatever an earlier instance already put on the context (later instances win per rule name) instead of replacing it, so a framework-level rule set and an app-level one can coexist.

### Data-only Rules

Unknown keys (`prerender`, `isr`, or your own) are **data-only**: they flow through matching and merging and are read from `event.context.routeRules` as the value you wrote (`rules.isr`, `rules.prerender`), with no runtime behavior. In TypeScript they need to be declared first, see [TypeScript](#typescript).

## Caching (`h3/rules/cache`)

H3 ships **no caching implementation** in `h3/rules`: `cache` (and the `swr` shortcut) need a registered `cache` rule handler, and matcher construction throws if a rule set uses them without one.

The ready-made handler is backed by [ocache](https://github.com/unjs/ocache) and lives in `h3/rules/cache`, so ocache — an **optional** peer dependency, install it alongside `h3` — stays out of every bundle that does not cache.

```ts
import { routeRules } from "h3/rules";
import { cache, createOcacheRuleHandler } from "h3/rules/cache";

// default: ocache with in-memory storage, wired with h3's response glue
app.use(routeRules({ "/blog/**": { swr: 60 } }, { handlers: { cache } }));

// custom storage / defaults (one handler instance per matcher):
app.use(
  routeRules(rules, {
    handlers: {
      cache: createOcacheRuleHandler({
        storage: myStorage, // ocache storage (minimal get/set) — note: process-global
        defaults: { staleMaxAge: 60 }, // ocache defaults incl. hooks (rule options win)
      }),
    },
  }),
);
```

The `cache` rule wraps the **matched route handler**, so it only applies where a route matched. Cache entries are keyed under the `"h3/route-rules"` group with a `<handlerScope>:<method>:<rulePattern>:<matchedRoute>` name by default. The scope is unique per handler instance _and_ per matched route handler, so two apps — or two matchers — never read or write each other's entries, even when they share the module-scoped `cache` export; the method keeps a body-less `HEAD` response out of the `GET` entry. Both are plain `cache` rule options and can be overridden, but an explicit `name` replaces the whole thing, isolation included.

The scope is not stable across processes, so a **persistent** storage backend is repopulated per process and not shared between workers. Pass `createOcacheRuleHandler({ id: "my-app" })` for stable keys — only when that instance serves a single app.

ocache resolves storage through one process-global slot, so the last `createOcacheRuleHandler({ storage })` call wins for every ocache consumer in the process (a conflicting override is warned about). Cache _entries_ stay isolated regardless, since isolation lives in the key.

> [!IMPORTANT]
> `Cookie`, `Authorization` and `Proxy-Authorization` are stripped from the request the cached handler sees, because none of them varies the auto-generated cache key — a handler rendering per-user content from a bearer token would otherwise have it cached anonymously, served to everyone, and advertised `public, s-maxage=N` to shared caches. Set `cache: { allowAuthorization: true }` to let the credential through; it then participates in caching (hashed into the key, merged into `Vary`), so each credential gets its own entry.
>
> If the runtime makes it impossible to remove the credential headers (immutable request headers _and_ a request that cannot be rebuilt), the cache rule fails the request with a `500` rather than dispatching. Serving would mean storing a credentialed response under a credential-free key for the whole TTL.

Headers listed in `varies` are visible to the cached handler. ocache filters them out of the forwarded request — which would leave a handler unable to read the very header its entry is keyed on — so the rule restores them for the dispatch. That is safe precisely because they are in the key and in the response's `Vary`: each value gets its own entry, never a shared one. A credential named in `varies` is the exception and stays stripped; `allowAuthorization` is the only switch that forwards one.

A handler's `Set-Cookie` reaches the requester whose request produced it, and never enters the cache entry. Cached copies therefore carry no cookie, and `allowCookies` does not change that — it is a request-side allowlist naming which cookie crumbs key the entry and reach the handler. Storing the cookie would replay one visitor's session to everyone the entry is later served to, so a route that must set a cookie on every response should not be cached.

A `Cache-Control` the handler sets that declares `private` or `no-store` is preserved as-is (ocache also refuses to store such a response), and `sendCacheControl: false` suppresses the synthesized header. Any _other_ handler-set `Cache-Control` is still replaced by the rule's synthesized `public, max-age=N, s-maxage=N` — use a `headers` rule to control it.

To plug in your own caching (no ocache at all), build a handler from the core factory. `defineCachedHandler` receives the matched route handler plus the merged rule options (with `group` / `name` pre-filled) and returns the cached wrapper — this is the integration point for frameworks such as Nitro:

```ts
import { createCacheRuleHandler } from "h3/rules";

const cache = createCacheRuleHandler({
  defineCachedHandler: (handler, opts) => myCachedHandler(handler, opts),
});
```

The declarative rule options (`RouteRuleConfig["cache"]`) are the ocache-compatible `CacheRuleOptions` schema owned by h3. Implementation hooks (`getKey`, `shouldCache`, `getMaxAge`, …) are not rule data — pass them via the handler factory's `defaults`.

## Proxying (`h3/rules/proxy`)

Like caching, the `proxy` rule is **opt-in**: its handler imports [`proxyRequest`](/utils/proxy#proxyrequestevent-target-opts), so it lives in `h3/rules/proxy` and stays out of every bundle that does not proxy. Register it explicitly — matcher construction throws if a rule set uses `proxy` without a handler:

```ts
import { routeRules } from "h3/rules";
import { proxy } from "h3/rules/proxy";

app.use(
  routeRules({ "/api/proxy/**": { proxy: "https://example.com/**" } }, { handlers: { proxy } }),
);
```

> [!TIP]
> To keep `cache` or `proxy` deliberately data-only (matched and readable from the context, but with no runtime behavior), pass `handlers: { cache: undefined }` / `handlers: { proxy: undefined }` instead of a handler.

## Options

`routeRules(config, options)` accepts:

| Option     | Description                                                                                         |
| ---------- | --------------------------------------------------------------------------------------------------- |
| `baseURL`  | Prefix every rule pattern (trailing slash trimmed).                                                 |
| `handlers` | Add or override rule handlers by name. `undefined` makes that rule data-only.                       |
| `memoize`  | Memoize match results per `method + pathname`. Enabled by default, see [Memoization](#memoization). |
| `preMerge` | Resolve each pattern's subsumption chain at startup, see [Pre-merging](#pre-merging).               |

### Custom Rules

A handler is `{ handler, order? }`, where `handler` builds an H3 [middleware](/guide/basics/middleware) from the matched rule and `order` controls execution order (lower runs first, default `0`; the built-ins occupy `-3`…`-1`).

The matched rule it receives is the wrapper — `{ options, route, params?, handler? }` — so a handler sees the merged `options` plus the provenance the context does not carry (`route` is the most specific pattern that contributed).

```ts
app.use(
  routeRules(
    { "/x/**": { shout: "hello" } },
    {
      handlers: {
        shout: {
          handler: (matched) => (event) => {
            event.res.headers.set("x-shout", String(matched.options).toUpperCase());
          },
        },
      },
    },
  ),
);
```

### Memoization

For a given `method + pathname` the merged result is fully deterministic, so it can be memoized: repeat requests skip the rule lookups, path canonicalization, merging and middleware construction, and a hot path becomes a single map lookup.

`routeRules()` memoizes **by default**. Pass `memoize: false` to resolve every request from scratch (each request then gets fresh result objects), or `memoize: { max }` to tune the cap. Entries are capped at `1024` by default with FIFO eviction, so unbounded dynamic paths cannot grow the cache.

For the lower-level matchers, memoization is decoupled from construction — opt in by wrapping any matcher with `memoizeRouteRulesMatcher(matcher, opts?)`, so an un-memoized bundle can tree-shake it away.

### Pre-merging

`preMerge: true` resolves each pattern's subsumption chain up front (at matcher startup, or at build time via the [compiler](#compiler-h3rulescompiler)) so per-request resolution takes only the most specific matched layer instead of merging all matched layers. Method-scoped and method-agnostic rules, `false` resets, and per-rule `params` behave exactly as with the default per-request merge.

It requires an unambiguous rule set. If two patterns partially overlap (for example `/a/*/c` and `/a/b/*`, where the most specific match would be ambiguous) or use patterns it cannot analyze (regex params), the **runtime matcher throws at startup**. The **compiler is fail-safe**: it logs a warning and falls back to plain compilation, so the build still produces a correct matcher.

## Matchers

`routeRules()` is the plug-and-play entry point. The pieces underneath are exported too, for framework integrations that need to match rules outside of the middleware:

```ts
import { createRouteRulesMatcher, normalizeRouteRules, memoizeRouteRulesMatcher } from "h3/rules";
import { cache } from "h3/rules/cache";

const matcher = memoizeRouteRulesMatcher(
  createRouteRulesMatcher(normalizeRouteRules(config), {
    baseURL: "/base",
    preMerge: true,
    handlers: { cache },
  }),
);

const { routeRules, routeRuleMiddleware } = matcher("GET", "/blog/post");
```

`normalizeRouteRules()` expands shortcuts (`swr`), normalizes string and boolean forms, and canonicalizes keys. Unlike `routeRules()`, `createRouteRulesMatcher()` takes **normalized** rules — that keeps normalization out of runtime bundles that don't need it.

A match result is `{ routeRules, matchedRules, routeRuleMiddleware }`: `routeRules` is the merged options map (what `routeRules()` puts on the context), `matchedRules` the same rules with their provenance, and `routeRuleMiddleware` the ordered chain.

`mergeMatchedRouteRules()` is the pure merge step (matched layers in, matched rules out), and `ruleHandlers` is the default handler registry (`headers`, `redirect`, `cors`).

## TypeScript

There are two interfaces, one per end of a rule: `RouteRuleConfig` describes what you **author**, `RouteRules` what the merge **resolves** — and since the merged value is the config value, a custom rule is declared once, in one shape, on both:

```ts
declare module "h3/rules" {
  interface RouteRuleConfig {
    /** Incremental Static Regeneration (handled at build time). */
    isr?: number | boolean;
    /** Add this route to the prerender queue. */
    prerender?: boolean;
    /** A data-only rule with no runtime handler. */
    audience?: "public" | "internal";
  }
  interface RouteRules {
    isr?: number | boolean;
    prerender?: boolean;
    audience?: "public" | "internal";
  }
}

// event.context.routeRules.audience -> "public" | "internal" | undefined
```

`RouteRuleConfig` is **closed** — unknown keys are compile errors, so a typo like `redirct` is caught at build time; the augmentation is what re-opens it for your key. `RouteRules` types the merged rules everywhere they surface: `event.context.routeRules`, a matcher's `routeRules`, and (as each rule's `options`) the `matchedRules` a rule handler is built from. Data-only rules still flow through normalization and merge untouched at runtime — augmentation only re-opens the typing.

`RouteRules` is h3's own interface, re-exported by `h3/rules`, so `declare module "h3"` merges into the same declaration — the spelling Nitro and the standalone `h3-rules` package already use. Only `RouteRuleConfig` is exclusive to `h3/rules`.

Redeclaring one of h3's **built-in** keys is supported too, not just adding new ones — a framework carrying its own rule shape can re-type `redirect`, `proxy`, … and the key then resolves to the augmenter's type instead of h3's:

```ts
declare module "h3" {
  interface RouteRules {
    redirect?: string | { to: string; status?: number };
    cors?: boolean;
  }
}
```

Any shape is accepted — including primitive and `false` arms, as above. `RouteRules` is unconstrained; h3's built-ins live on a separate `BuiltinRouteRules` and are composed in only for the keys nobody redeclared. The type on the context is that composition, exported as `ResolvedRouteRules`. A redeclaration **replaces** h3's built-in rather than intersecting with it, and a key left to h3 keeps its exact option type, so `rules.redirect?.to` reads without narrowing.

> [!NOTE]
> h3 composes in only its own built-ins, and declares no index signature. Contributing a blanket `[key: string]: unknown` to the shared interface would turn every other module's augmentation into a type error — which is why an undeclared data-only key is readable at runtime but not typed until you declare it.

Two more types are exported for integrations: `NormalizedRouteRules` (one pattern's rules after `normalizeRouteRules()` — `RouteRules` plus `false` resets and arbitrary names) and `MatchedRouteRule` (a merged rule with its provenance, what a rule handler receives).

## Security

### Path Spellings

A rule is matched against **every spelling of the request path a consumer can resolve**, not just the one h3 dispatched on — otherwise a rule could be dodged by re-spelling the path it applies to.

[`event.url.pathname`](/guide/api/h3event#pathname-encoding) decodes only the escapes that are _needless_ — the ones whose character survives URL serialization, so `/%40admin` is already served as `/@admin`. What it still carries encoded is the separators (`%2f`, `%5c`), `%25` at any nesting depth, the escapes the serializer would re-add (`%20`, non-ASCII), and the C0 controls. A pattern, meanwhile, is written with the character itself. So each request is also resolved against its canonical reading (encoded separators decoded, `.` / `..` resolved), its slash-merged reading (what a downstream like nginx `merge_slashes` resolves), and its percent-decoded reading:

```ts
routeRules({
  "/@admin/**": { redirect: "/elsewhere" },
  "/a admin/**": { redirect: "/elsewhere" },
});

// GET /@admin/data     -> matched
// GET /%40admin/data   -> matched  (h3 serves it as /@admin/data)
// GET /a%20admin/data  -> matched  (a proxied backend would serve it as "/a admin/data")
// GET /a%2520admin/x   -> matched  (…and so would one that decodes twice)
// GET /admin%2fpanel   -> matched against /admin/panel too
```

An alternate reading may only **add** a rule, or override one with an equal-or-more-specific pattern — a broader pattern reached through a crafted path can never downgrade a rule the served path resolved.

A rule the served path _reset_ with `false` is covered too, by the rule's **polarity**. A reset is applied as a deletion, so a reset rule would otherwise be indistinguishable from one that never matched, and a broader alternate reading would re-add it at that broader pattern's breadth:

- A rule that **permits** something stays reset. Re-adding it could only loosen the response, so the exemption wins — a `cors: false` on a private subtree cannot be undone by a crafted spelling of the same path. Every built-in (`cors`, `redirect`, `headers`, `cache`, `proxy`) is of this kind.
- A rule that **restricts** something is still re-added. A restriction is fail-closed, so an exemption granted by a single-segment pattern does not follow a path that decodes to more segments than that pattern covers.

Handlers declare which they are via `RuleHandler.restricting`, which defaults to `false`. No built-in sets it.

> [!IMPORTANT]
> A **custom** rule handler that restricts (an auth gate, a rate limit, an IP allowlist) must set `restricting: true`, or a `false` reset on one reading will exempt it on every other reading. The default is the safe choice for a permission and the wrong one for a restriction, and nothing warns. Rules with no handler at all (data-only rules a consumer such as Nitro acts on itself) cannot carry the flag — a consumer treating one as a gate needs its own reasoning at the point of use.

One residual, in the fail-safe direction: a permission reset is never resurrected, even by a reading that is a faithful re-spelling of the path that granted it. `{"/**": { cors }, "/app/*": { cors: false }}` keeps the exemption on `/app/a%2fb`, whose decoded reading has two segments and arguably falls outside the single-segment pattern that reset it. Every case this gets wrong errs toward _not_ applying a permission.

The reverse spelling is normalized too: a pattern written `/a%20admin/**` is decoded to `/a admin/**` at config time, so it does not silently cover only the encoded form. A rule key resolves escapes exactly as an h3 route pattern does, so an escaped rou3 metacharacter _becomes_ that metacharacter — `"/a/%3Aid"` is the `:id` param pattern, and `"/f/%2A%2A"` a catch-all, matching `app.get("/a/%3Aid")`. Only `%2f`, `%5c` and `%25` stay encoded and match literally, since decoding one would change the pattern's segment count.

Dispatch is unaffected: routing still uses `event.url.pathname` as served, and `redirect` / `proxy` still forward the raw path bytes.

### `HEAD` and Preflight Requests

`HEAD` requests are served by the matching `GET` route ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#name-head)), so `GET`-scoped rules apply to `HEAD` too — otherwise a rule keyed `GET /admin/**` could be dodged with a `HEAD` request. An explicit `HEAD` key still merges over (and can reset) the `GET` ones.

A CORS preflight arrives as `OPTIONS`, so a `cors` rule scoped to the method the browser announces in `Access-Control-Request-Method` is resolved for the preflight as well. Only the `cors` rule is taken from that lookup — never any other rule scoped to that method, since browsers send preflights without credentials and a gate lifted out of it would reject every preflight.

### Headers on an Outer Rule's Response

`headers` sits at order `-1`, so it wraps every rule that runs inside it — but not one that runs _outside_ it. A response produced by an outer rule (the `cors` preflight answer, or a custom handler in the free `-2` band) short-circuits before the headers middleware is entered, so the `headers` rule is not applied to it. Every other response goes through it, including error responses raised further in (a `404`, or a handler that throws).

If a header must be present on such a response too, set it from global middleware registered before `routeRules()`, and set it on `event.res.errHeaders` as well — an error response is built from that bag, not from `event.res.headers`.

### Redirect and Proxy Targets

For a `/**` target, the matched tail is appended and the resulting path is checked against the target's own base; a request that would escape it (for example via an encoded `..%2f` traversal) is rejected with `400`.

### CORS Credentials

`credentials: true` requires an explicit `origin` (allowlist or validation function). Combining it with a wildcard origin throws at startup, since `Access-Control-Allow-Origin: *` is invalid for credentialed requests.

## Compiler (`h3/rules/compiler`)

For build-time codegen, compile a rule set into a `findRouteRules` function so Rou3 stays out of the runtime bundle:

```ts
import { compileRouteRules } from "h3/rules/compiler";

const mod = compileRouteRules(config, {
  preMerge: true, // optional: bake pre-merged chains into the generated matcher
});

mod.code; // whole module (also `String(mod)` / template interpolation)
// -> import { headers as __ruleHandlers__$headers } from "h3/rules";
// -> export const findRouteRules = (method, path) => ...;
```

`compileRouteRules` returns the module split into its two composable halves — `imports` (the handler `import` statements) and `body` (the `export const findRouteRules = …` declaration) — plus `code` (the whole module, same as `String(mod)`). Take `code` to write a standalone module, or hoist `imports` and inline `body` to weave the matcher into a larger generated module.

The compiler entry points normalize their input themselves (compilation is build-time, so the pass is free) — pass authored config directly. An already-normalized rule set is equally valid input, since normalization is idempotent.

At runtime, wrap `findRouteRules` with `createMatcherFromFind(findRouteRules)`, composing `memoizeRouteRulesMatcher` around it for [memoization](#memoization). Compiled and runtime matchers produce identical results.

> [!IMPORTANT]
> The matcher API takes the method **already uppercased** — `findRouteRules`, `createMatcherFromFind` and `createRouteRulesMatcher` all compare it as given. The `routeRules()` middleware normalizes for you; a hand-written wrapper must pass `event.req.method.toUpperCase()`, or a lowercase-spelled request will match no method-scoped rule at all and skip its gate.

> [!NOTE]
> Rule options are embedded as JS object literals, so they must survive a JSON round-trip. A function, `Date` or `RegExp` in a rule option (for example a `cors.origin` validation function) fails compilation with an explicit error instead of silently diverging from the runtime matcher.

### Specificity Guard

`createMatcherFromFind` applies a **specificity guard by default**. When one of a path's [alternate readings](#path-spellings) (canonical, slash-merged, percent-decoded) resolves a rule differently from the served path, the alternate reading may only override with an equal-or-more-specific pattern — so a broad `/**` rule can never downgrade a narrower `/admin/**` one on a crafted `%2f` / `%2e%2e` path.

The default guard is dependency-free, so a compiled bundle stays free of Rou3. It decides containment from pattern shape, which is a **conservative approximation** of the exact relation: it allows only containment it can prove, so it never permits an override the exact relation would reject, but it is stricter — where it cannot decide (a named catch-all such as `**:rest`, a regex or partial param, or a modifier param like `:page?` / `:path*`), it keeps the rule the served path resolved rather than applying the narrower one. Use [`matcher: true`](#matcher-export) to have the compiler bake the exact relation into the generated module — recommended whenever rule keys use modifier params — or pass your own predicate as the second argument, or `() => true` to disable the guard.

Ordering matched layers by specificity does **not** go through this predicate: it uses a rank computed when the rule set is built, so a compiled matcher without the baked relation still resolves the same rules as the runtime matcher.

### Matcher Export

To skip the hand-written wrapper, pass `matcher` so the generated module exports a ready-to-use matcher alongside `findRouteRules`:

```ts
compileRouteRules(config, { matcher: true });
// -> export const findRouteRules = …;
// -> import { createMatcherFromFind } from "h3/rules";
// -> export const matcher = createMatcherFromFind(findRouteRules, /* baked specificity guard */);

// rename the export, or bake in memoization:
compileRouteRules(config, { matcher: { name: "routeMatcher", memoize: true } });
// -> import { createMatcherFromFind, memoizeRouteRulesMatcher } from "h3/rules";
// -> export const routeMatcher = memoizeRouteRulesMatcher(createMatcherFromFind(findRouteRules, …));
```

`matcher: true` names the export `matcher`; pass a string to rename it, or `{ name?, memoize? }` to also wrap it in `memoizeRouteRulesMatcher` (`memoize: { max }` tunes the cap). `memoizeRouteRulesMatcher` is imported **only** when `memoize` is set, so an un-memoized matcher export still tree-shakes it away. The infra import counts toward `mod.imports`.

### Handler Sources

The generated module imports **only the rule handlers the rule set uses**. Most built-ins are a named export of `h3/rules` (`headers`, `redirect`, `cors`), except the opt-in subpath handlers: `cache` comes from `h3/rules/cache` and `proxy` from `h3/rules/proxy`, so their dependencies only enter the bundle when a matching rule exists.

Where each handler is imported from is controlled by `runtimeRules` — a record keyed by rule name whose value is either a module id (the module must export a member named exactly as the rule key) or `{ source, export }` when the export is named something else. It is merged **over** the built-in preset (`DEFAULT_RUNTIME_RULES`), so you only list what you add or change. Handlers sharing a source collapse into one import statement:

```ts
import { compileRouteRules } from "h3/rules/compiler";

compileRouteRules(config, {
  runtimeRules: {
    cache: "#nitro/cache", // repoint the built-in cache at your own module
    isr: { source: "#nitro/rules", export: "handleISR" }, // custom rule + export
  },
});
// -> import { handleISR as __ruleHandlers__$isr } from "#nitro/rules";
// -> import { cache as __ruleHandlers__$cache } from "#nitro/cache";
// (redirect, headers, … still import from "h3/rules" when used)
```
